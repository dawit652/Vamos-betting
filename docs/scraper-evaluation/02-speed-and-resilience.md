## 2. Method

**Data.** `openfootball/football.json`, blobless clone, head `e6744429ee39` (2026-09-22T09:33:49Z). The live file on raw.githubusercontent.com was compared with the head on 2026-10-29 (same 380 matches, 50 scored, latest score dated 2026-09-20, ETag served, `cache-control: max-age=300`); `git ls-remote` shows the same head. Files: `2026-27/{en,es,de,it,fr}.1.json` (6 to 8 commits each), `2025-26/{en,es}.1.json` (22 and 14 commits). Second source: `vaastav/Fantasy-Premier-League` head `d7b05b51d137` (2026-10-22), `data/2025-26/fixtures.csv` (12 commits) and `data/2026-27/fixtures.csv` (4 commits).

**Definitions.**

- Lag = commit time (committer date, UTC) minus (kickoff + 105 min). Kickoff uses the league's IANA zone via the adapter's own `zonedToUtc`. A score counts when it has `score.ft` (what the adapter accepts). The first snapshot of a file is excluded (the lag would be unknown).
- Right-censoring: matches played but not yet scored are left out of the main lag; a second line adds them with the wait so far as a lower bound.
- Matches are keyed by `team1|team2` (unique per season). A snapshot is unusable when it is not valid JSON or fewer than 90% of its records have a date.
- Commits become visible about 5 minutes later (CDN `max-age=300`); not added to the numbers.

**Commands** (repo root, scratch dir `/tmp/claude-0/-home-user-Vamos-betting/d1397695-bb43-5462-ba14-3ed7d2c3f21e/scratchpad/eval-speed/`):

```
git clone --filter=blob:none https://github.com/openfootball/football.json of
git clone --filter=blob:none --no-checkout https://github.com/vaastav/Fantasy-Premier-League fpl/repo
pnpm --filter @vamos/scraper-app exec tsx src/eval/speed-freshness.ts of out.json fpl/repo     # P1
pnpm --filter @vamos/scraper-app exec tsx src/eval/speed-latency.ts <archiveDir> fresh.dump out.json   # P3 simulated
pnpm --filter @vamos/scraper-app exec tsx src/eval/speed-settle.ts snapshot.json <archiveDir> fresh.dump out.json 100   # P3 settlement
pnpm --filter @vamos/scraper-app exec tsx src/eval/speed-checks.ts snapshot.json <archiveDir> fresh.dump out.json     # P4 checks
```

`fresh.dump` is `pg_dump -Fc vamos_eval_speed` after `DATABASE_URL=postgres://vamos:vamos@localhost:5432/vamos_eval_speed pnpm db:migrate && pnpm db:seed`; the harness (`speed-lib.ts`) resets the scratch database from it with `pg_restore --clean`, refuses any other database name, uses Redis db 10, keeps the production fetcher defaults (3 attempts, back-off, 5 min breaker, 5 MiB, 15 s timeout) and injects only clock, sleep and transport. The simulated and check runs use the real adapters, gates, promotion and scheduler code on a real Postgres. The latency documents are synthetic (one Arsenal v Chelsea fixture): they are the input of a timing simulation, not data about the world. The checks and the settlement timing use the real 2026-27 en.1 document at its head commit, with the clock set to 2026-10-01 (the next fixtures after the September international break are 10 October; at 22 September no event is inside the 14-day horizon).

**Missing times.** In es/de/it/fr 2026-27, 290 of 380, 198 of 306, 260 of 380 and 192 of 306 fixtures have no kickoff time at the latest commit. The adapter drops those records (`missing_time`), so no event exists for them and a played match without a time never gets a result. The time is published a median 18 to 52 days before kickoff (es.1 p10: 11 days, fr.1 p10: 17 days), so creation is not late; the risk is a played match whose time was never published. 10 es.1 matches are in that state now.

**The 0-0 problem.** In the current file a 0-0 draw is written `"score": [0, 0]` (a bare list), while other scores are `{"ht": [..], "ft": [..]}`. The adapter requires an object and drops the record with `bad_score`. All 27 bare lists in 2025-26 en.1 are real 0-0 draws: FPL has exactly 27 finished 0-0 fixtures at those same kickoffs, and 5 of 5 in 2026-27. Such a match has no result observation at all, so it never reaches `result_unverified`: nothing is raised for a person. (Earlier commits wrote the same draws as `{"ft": [0, 0]}`, which parses.) Other format variants in the real history: `"score": {}` for unplayed matches in the first 2025-26 commit (dropped as `bad_score`), 11 clubs renamed on 2025-11-04 (all 308 `team1|team2` keys changed; our observation key uses the raw names, a known limit), and the two unusable snapshots (invalid JSON on 2025-12-04: a missing `{` after `"score":`; no dates at all on 2026-05-23).

**What this means for "final whistle to result known to us".** From openfootball the score is in the file a median of 2.8 days (p90 6.2 days) after the whistle in a good month, 16.7 days (p90 51 days) over the whole 2025-26 season, and nothing at all since 22 September. It is never available within hours. Our own pipeline adds 15 to 19 minutes (two sources) or a human (one source), see 3.2. So with this source, final whistle to settled bets is days, not minutes. The 5-minute polling around the final whistle is spent polling a file that changes about twice a week.

### 3.2 P3: our own pipeline, from the code and measured

Constants read from code: results poll every 5 min from kickoff + 90 min to + 6 h, else 15 min (a source with fixtures and results purposes takes the faster of the two; `cadence.ts`, `scheduler.ts`); scheduler tick 30 s; promote 60 s; R1 earliest result at kickoff + 105 min; R4 wait `SCRAPER_RESULT_CONFIRM_MINUTES` = 15 min (minimum 5); R6 single source opens `result_unverified` at kickoff + 105 min + 6 h; staff confirmation is picked up on the next promotion pass and stays valid for 24 h; outbox dispatch every 1 s; settlement is a BullMQ job (concurrency 2) with a 30 s sweep that only looks at events resulted more than 60 s ago.

Timeline, minutes after the score becomes visible at the source (V = visibility; K = kickoff):

| Step                                     | (a) two upstreams, no human            | (b) one upstream plus a trader                                                                       |
| ---------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Next poll sees it                        | 0 to 5 (measured 0 to 4)               | 0 to 5                                                                                               |
| Gate wait                                | R4: 15 after the last change           | R6: until K + 7 h 45 min if V is earlier; none if V is later                                         |
| Promotion pass                           | up to 1                                | up to 1                                                                                              |
| Human                                    | none                                   | trader pickup (not measured; assumed 0 in the simulation)                                            |
| Apply (`applyConfirmedResult`)           | 22.7 ms                                | 22.7 ms                                                                                              |
| Outbox dispatch, queue                   | up to 1 s (from code)                  | up to 1 s (from code)                                                                                |
| Settle 100 bets                          | 0.6 s (2 lanes)                        | 0.6 s (2 lanes)                                                                                      |
| **Best / typical / worst, V to applied** | **15 / 17 / 19 (measured, 15 phases)** | **1 min (score first seen long after K + 7 h 45) / human / 355 + human (score seen at K + 110 min)** |

Simulated with the real scheduler, gates and promotion and a 30 s clock (`speed-latency.ts`), over 15 poll phases: first seen 0 to 4 min (median 2), applied 15 to 19 min (median 17, p90 19). The R4 rule dominates (15 min exactly after the first sight); the extra 0 to 4 min is poll phase. Target p90 <= 30 min: met. Scenario C (two upstreams, competition not on auto results, trader answers at once): item opens at the same 15 to 18 min, applied 60 s later. Scenario B: with a single upstream and the score visible at K + 110 min, the item opened 355 min later (K + 7 h 45 min) and was applied 60 s after that; with the score first seen 24 h after kickoff, the item opened at once and was applied after 60 s. So the single-source path adds a fixed 6-hour wait even when the match is plainly over; that wait only matters for a faster source than openfootball.

Settlement (`speed-settle.ts`, 100 singles + 20 doubles on one scraped event, real `placeBet`, real `applyConfirmedResult`, real `settlePlacedBet`, one transaction per bet): apply 22.7 ms; `settlePlacedBet` median 10.9 ms, p90 16.2 ms, max 36.8 ms with 2 lanes (60 bets in 344 ms), median 10 ms sequentially (60 bets in 598 ms); `listBetsToSettle` 4.4 ms; 113 of 120 bets final, the 7 left are doubles whose second leg is on an event not yet resulted, as expected; the sweep then finds 0. Extrapolating the 2-lane rate: 1 000 bets about 5.7 s, 10 000 about 57 s (linear extrapolation, one event, no contention with live betting). _Partial:_ the BullMQ hop and the outbox dispatcher were not run (no servers), their cost is taken from the constants (1 s dispatch interval; worst case if a job is lost: the sweep, at most 30 s plus the 60 s grace).

**What a true live feed needs that does not exist.** Version 1 has `fixture` and `result` observation kinds only; `result` carries a final score. Task 08A of `docs/scraper-plan/08-live-scores-and-extensions.md` would add a live observation kind and live polling. Today, none of these exists: a live observation (minute, period, running score) stored per source; a seconds-level cadence (the minimum host interval is 2 s, the scheduler tick is 30 s, the fastest poll is 5 min); a gate for live state that never settles a market from a lone feed; events that can leave `scheduled` (R1 states scraped events never go live); a source that actually delivers live data (openfootball does not). Not designed here.

## 5. Limits of this evaluation

- One reference source and one second source; both are volunteer-kept datasets, not what a production feed would look like. Freshness figures apply to them only.
- Lag uses commit time. The real arrival at our scraper adds the 0 to 15 min poll phase and about 5 min of CDN cache; not added to the P1 table (the simulated P3 includes poll phase, not CDN).
- Matches played but unscored are right-censored; the main table leaves them out, the "pending" column bounds them. Fixtures without a time are measured against the end of their calendar day (none ended up in a lag table: n=0 or 1).
- P3 (a) is simulated with synthetic documents on the real code; the trader answers at once (best case, a person is slower). The queue (BullMQ) was not run; `resultedAt` in the database uses the database clock, not the injected one.
- The identical-snapshot and absence checks ran on 10 events, with one source and betting closed. They do not cover concurrent passes or restarts.
- The replay, the failure scenarios and throughput were not measured; the report makes no claim about them. Gap 4 and gap 7 are derived from code and history, not from a replay.
- `apps/scraper` typecheck currently fails only because of another evaluator's `odds-*.ts` files; the `speed-*.ts` files typecheck on their own.

## 6. Not done, and how to run it later
