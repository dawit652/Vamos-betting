## Findings

### 1. HIGH: one event is decided once per cluster, so its kickoff flips back and forth

- **Where:** `apps/scraper/src/pipeline/promote-fixtures.ts:221-258` decides each
  cluster against one snapshot of events; `:347-385` (`applyKickoff`) locks the
  event but does not check that its start is still `decision.from` or that it
  still has no bets.
- **Scenario:** event E at Nov 2 15:00. Sources a, b (independent) move it to
  Nov 4; sources c, d still say Nov 2. The two groups are more than 36 h apart,
  so they form two clusters, both matching E (45-day window). Pass 1 moves E to
  Nov 4 (F4a); pass 2 moves it back (two independent sources, "earlier"); and so
  on. One updated source plus two stale rows from sources without external ids
  does the same, so the "fails closed" claim in known-limits is wrong. Near
  kickoff the minimum-lead rule freezes whichever date E has: betting can stay
  open past the real kickoff.
- **Confirmed:** the start alternated on each of 4 passes, with 4
  `scrape.fixture.kickoff_moved` audit rows.
- **Fix:** group clusters by matched event before deciding; more than one
  cluster for an event opens a single `kickoff_change` (`sources_disagree`) and
  applies nothing. In `applyKickoff`, re-read `start_time` and bets under the row
  lock and abort if the start differs from `decision.from` or bets now exist.

### 2. HIGH: a `create` decision on an existing `feed_ref` silently moves and re-prices that event

- **Where:** `promote-fixtures.ts:303-345` (`applyCreate` checks `result.created`
  after the upsert ran); `packages/db/src/catalog/fixtures.ts:137` (update path
  moves `start_time` and re-prices open selections).
- **Scenario:** a trader reschedules a postponed event 60 days later. A stale
  source still lists the original date; F3 finds no event within 45 days, so the
  decision is "create" with the same feed_ref; `upsertFixture` moves the event
  back and re-prices it without F4, O3 or a trader; no audit row;
  `summary.created` counts it.
- **Confirmed:** the start went from 2027-01-01T15:00Z back to 2026-11-02T15:00Z.
- **Fix:** make the create path insert-only; if the row exists, change nothing and
  open `fixture_conflict` (`feed_ref_exists`). Let `matchEvent` treat an event with
  the same feed_ref as a candidate whatever the window.

### 3. HIGH: a rejected staff confirmation is replayed later, even after a person dismissed the reopened item

- **Where:** `apps/scraper/src/pipeline/promote-results.ts:380` (only replay
  guard: `payload.reopenedFor` on another item); `:477-485` reopens by upserting
  into the open item of the same kind and subject; each gate pass replaces that
  payload (`pipeline/common.ts:80-98`, `packages/db/src/scrape/review.ts:77-86`),
  dropping `reopenedFor`.
- **Scenario:** item A (`result_ready` 3-1) resolved `apply_result`; source B
  changes to 3-2, confirmation rejected, B' opened with `reopenedFor: A`; B goes
  back to 3-1, the gate re-raises `result_ready` and overwrites B''s payload; a
  person dismisses B'; the next pass applies A. With `result_unverified` a single
  source flipping 3-1 → 3-2 → 3-1 is enough.
- **Confirmed:** `applyStaffConfirmations` returned `{applied:1}`; event finished 3-1.
- **Fix:** make a rejection final for A in a place the gate cannot overwrite (for
  example skip A when an audit row `scrape.result.confirmation_rejected` targets
  it, a `consumed_at` column, or only act on items resolved after the newest
  closed item of the same kind and subject).

### 4. HIGH: the generic adapters treat "has a score" as "finished", so live scores can settle

- **Where:** `packages/scraper/src/adapters/generic-json.ts:373`,
  `generic-html.ts:287`: `status ??= score ? 'finished' : …`; the status field is
  optional (`generic-json.ts:165`) and a blank or null value reaches this line.
- **Scenario:** two generic sources of different upstreams show in-play scores
  with no (or a blank) status. Both produce "finished 1-0". With a delayed
  kickoff the match is still live at kickoff + 105 min; R1, R2, R4 pass; with
  auto results on, 1-0 is applied; a late goal needs an R8 correction.
- **Confirmed:** at adapter level (status null or "" plus a score came back
  `finished`); the rest by reading.
- **Fix:** when a score is configured, require a status field; a missing or blank
  value uses `status.default` if set, otherwise drops the record with
  `missing_status`; never derive `finished`; forbid `default: 'finished'`.

### 5. HIGH: switching a competition off does not stop kickoff moves or automatic results; `extraTime` is never read

- **Where:** `packages/scraper/src/gates/result.ts:313` checks only
  `autoResults`; `gates/fixture.ts` `decideExisting` (`:303-393`) never reads
  `enabled` (only `decideNew` at `:265` does); nothing reads `extraTime`.
- **Scenario:** a trader switches a competition off during an incident; with auto
  results still on, agreeing sources keep moving kickoffs and applying results.
  A knockout competition with `extraTime` on, fed by a source wrongly configured
  as regular time, is applied without an extra check.
- **Confirmed:** with `enabled=false` the run showed `kickoffMoved:1`, then
  `applied:1`.
- **Fix:** policy disabled → `decideResult` never returns apply and
  `decideExisting` proposes `kickoff_change` instead of moving; `extraTime` on →
  never auto-apply; document `enabled` in `types.ts` and `policy.ts`.

### 6. MEDIUM: the staff path applies a half-time score that a current source disputes, and skips the kickoff check

- **Where:** `promote-results.ts:423-451`: dissent compares only full time; half
  time only on supporting observations; no kickoff-tolerance or R10 basis check.
- **Scenario:** `result_ready` 2-1 (HT 1-0) approved; before apply source B
  corrects HT to 0-0; HT 1-0 is applied on an event with a half-time market.
- **Confirmed:** `{applied:1}` with HT 1-0 while src-b says 0-0.
- **Fix:** dissent with `scoreContradicts(proposed, obs.score, event.needsHalfTimeScore)`;
  reject when the event needs a half time and the proposal has none; reject when
  any observation's kickoff differs from the event start by more than
  `KICKOFF_TOLERANCE_MS`.

### 7. MEDIUM: a 304 counts as "nothing seen", and the ETag is stored before the page is accepted

- **Where:** `apps/scraper/src/pipeline/run-source.ts:255` (304 skipped:
  `last_seen_at` not updated, no raw row); `:350` (`source_broken` closed on any
  ok run); `packages/scraper/src/fetch/polite-fetcher.ts:406` (ETag remembered on
  every 200 before the shape check and storage).
- **Scenario a:** an unchanged fixture page for 48 h gets 304s; "last listed"
  freezes; every listed event gets `fixture_missing`, a false absence signal.
- **Scenario b:** markup changes, the 200 is judged broken but the ETag is kept;
  the next run gets 304, ends ok and auto-closes `source_broken`; old
  observations keep voting.
- **Confirmed:** both reproduced.
- **Fix:** on 304, record a raw row reusing the previous hash and bump
  `last_seen_at`/`run_id` of that URL's observations; add
  `fetcher.forgetValidators(url)` when a page is broken or storing fails; do not
  close `source_broken` on a run in which no page was parsed.

### 8. MEDIUM: removing a wrong alias never un-maps stored observations

- **Where:** `packages/db/src/scrape/observations.ts:266-274`, `:286-294` (old
  ids kept); `run-source.ts:484-514` (re-resolution only for null ids); the
  comment at `aliases.ts:178` ("until re-resolved") never happens.
- **Scenario:** alias "United" points to the wrong team; a trader removes it;
  current observations keep the wrong team id and keep voting.
- **Confirmed:** after removal, two runs and two promotions, still Arsenal.
- **Fix:** `upsertObservation` writes the resolution it is given, including
  null (explicit input); re-resolve resolved rows whose names match a removed or
  changed alias (or all rows of the sport after any alias change).

### 9. LOW: approved staff items older than the newest 200 of their kind are never applied or rejected

- **Where:** `promote-results.ts:371` (`listReviewItems({kind, limit: 200})`).
- **Fix:** query resolved items of those kinds resolved within the last 24 h, or
  page until older than 24 h.

### 10. LOW: unknown-name review items are opened in unsorted order, so concurrent runs can deadlock

- **Where:** `run-source.ts:142-173`, `:463-470`.
- **Fix:** sort by (kind, subject key) before opening, or open them in their own
  transaction after the observations.

## Not covered

- `generic-html` selectors skimmed; fetcher robots and redirects read for the
  allow-list only; DNS rebinding out of scope.
- `/admin/feed/*` routes were being written at the time and were not reviewed.
- Races read but not reproduced: pruning a snapshot that a result marks as
  evidence in the same window; the 20,000-row limit on current observations can
  cut through one fixture and hide dissent; a dissenting observation that becomes
  unresolved after a team rename drops out of R3.
- Ratings maths, price-sanity thresholds, `main.ts` and the health server were
  skimmed only. Result decisions are applied without re-reading observations.
